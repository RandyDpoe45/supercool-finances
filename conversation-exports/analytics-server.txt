● Confirmed both forks in the code — and they matter, because "full enrich" as
  literally described ("emit reversed/failed event types too") hits two things
  that don't have a clean source on the finished money path:

  1. FAILED is never persisted. Searching the whole balance-service src, there
  is no write of status: TransactionStatus.Failed anywhere — only POSTED,
  EXPIRED, CANCELLED, REVERSED. So there is no source row from which to emit a
  transaction.failed event. (DATA-MODEL's idempotency note asserts "a business
  failure produces a FAILED transaction," but the code never implemented it —
  pre-tx validation failures release the in-progress key instead.) Emitting
  failed events would mean building FAILED-transaction persistence first —
  net-new money-path behavior, not an event enrichment.

  2. REVERSED is already faithfully represented. A reversal
  (approval.service.ts) does two things in one tx: flips the original POSTED → 
  REVERSED (transitionToReversedInTx — a status change, no money moves on that 
  row), and posts a compensating transaction via the reducer with
  reversesTransactionId set + forced:true (the mirrored, balanced legs — this is
  where the money actually moves). That compensating movement already emits
  transaction.posted (thin today, enriched after this work). So the money
  reversal is captured. A separate transaction.reversed event on the original
  would be a pure status-marker — and if it echoed the original's legs, summing
  deltas in aggregation would double-count. So it has to be an empty-legs marker
  or not emitted at all.
