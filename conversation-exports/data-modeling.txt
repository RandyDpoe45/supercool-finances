● Good questions — these are exactly the joints where the entity model has to be
  pinned down. Answers, grounded in the specs/ADRs, one by one.

  1) approval_request — what it's for and when it fires

  It's the persistence of maker-checker (four-eyes) for admin money operations
  (ADR-8 (docs/DECISIONS.md)). It exists only on the /admin plane, and only for
  privileged actions that can move or reshape money across customers — never on
  the normal customer transfer path.

  It fires when an admin initiates one of the approval_action operations:
  - reversal — undo a posted transaction (compensating entries).
  - limit_change — change a customer's or global limits.
  - adjustment — a manual balance correction.

  Lifecycle:

  Admin A submits reversal of tx X  → approval_request{ status: PENDING,
  maker_id: A, checker_id: NULL, payload: {…} }
  Admin B (≠ A) approves            → status: APPROVED, checker_id: B,
  decided_at
  Service executes the approved op  → status: EXECUTED, executed_at  +  writes
  the real ledger/reversal  +  writes audit_log
  Admin B rejects instead           → status: REJECTED, decided_at (nothing
  moves)

  The point is that no single admin can unilaterally move money — the row
  records the proposer, the approver, the proposed payload, and enforces
  checker_id <> maker_id. Only an APPROVED row can transition to EXECUTED. The
  actual money movement (the reversal's compensating ledger entries) happens at 
  execution, not at submission.

  2) idempotency_key — the client half vs. the server half

  You've spotted the real subtlety: there are two different things in that row,
  and only one is client-supplied.

  - key — client-supplied. The client generates a unique token (a UUID) per
    logical operation and sends it in the Idempotency-Key header. On a retry
    (timeout, dropped response) it sends the same key. We never compute this;
    it's opaque to us. It answers: "is this the same logical attempt?"
  - request_fingerprint — server-computed. A guard against the client reusing a 
    key for a different request. It answers: "…and is it really the same 
    request, or did you accidentally reuse the key?"

  How they reconcile on each request:

  ┌──────────────────────────┬──────────────────────────────────────────────┐
  │        Situation         │                  What we do                  │
  ├──────────────────────────┼──────────────────────────────────────────────┤
  │ Key not seen (for this   │ Insert in_progress, process, store           │
  │ owner_id)                │ response_body, mark completed.               │
  ├──────────────────────────┼──────────────────────────────────────────────┤
  │ Key seen, completed,     │ Replay the stored response — money moved     │
  │ fingerprint matches      │ once.                                        │
  ├──────────────────────────┼──────────────────────────────────────────────┤
  │ Key seen, in_progress    │ A concurrent retry is mid-flight → return    │
  │                          │ "in progress", don't double-process.         │
  ├──────────────────────────┼──────────────────────────────────────────────┤
  │ Key seen, fingerprint    │ 409 Conflict — key reused with different     │
  │ differs                  │ parameters (Stripe-style).                   │
  └──────────────────────────┴──────────────────────────────────────────────┘

  Now your sharper question — "does it make sense to hash all those values 
  (method+path+body)?" No, and you're right to push. Hashing the raw body is
  brittle (whitespace, field ordering, extra fields all change the hash and
  cause false 409s). The fingerprint should be a hash of the canonical business 
  tuple only:

  fingerprint = hash( type, source_account_id, destination (payee_id |
  dest_account_id), amount, currency )

  Method+path are already implied by the endpoint. That's the refinement I'd
  make to the doc: request_fingerprint = hash of the semantic transfer 
  parameters, not the raw HTTP body. And the unique index stays (owner_id, key)
  so keys are namespaced per caller (two customers can independently pick the
  same UUID; one user can't probe another's key).

  3) Should the hold relate to the external account too?

  Your mental model is right — ledger_entry is the per-account view of a
  transaction (each account effectively has its own ledger), and hold is the
  reservation analog. But here's the key timing fact that answers your question:

  At PLACED, no money has moved yet. A hold reserves funds on one account — the
  customer's — bumping account.held so available drops. Nothing touches the
  destination or the clearing account until SETTLED, and that's the moment the
  double-entry ledger posts (debit customer, credit clearing:rail-outbound). So
  the hold is fundamentally a single-account reservation; a hold doesn't have a
  "both sides" the way a ledger transaction does.

  The destination is reachable, just not by a direct FK on the hold:
  - hold.transaction_id → transaction.payee_id → external_payee = who the money
    is going to.
  - hold.rail + hold.external_ref = the handle that reconciles the hold against
    that rail's settlement feed (ADR-14 (docs/DECISIONS.md)).

  So the linkage you want exists, via the transaction. I'd not add a direct
  hold.payee_id — it would be denormalization derivable through the transaction.
  The only reason to add one is if we needed fast "all holds against payee X"
  queries, which no spec-04 requirement calls for. My recommendation: leave the
  hold single-account, keep rail/external_ref for reconciliation.

  4) Is external_payee the external account the user sends to?

  Yes — it's the enrolled external beneficiary/destination (with the cooling-off
  gate before it can receive money, spec 04). destination_ref is the masked
  identifier of that external account.

  One important distinction, though: the payee is not an account row in our 
  ledger. External money's counter-leg in the double-entry is the clearing 
  account (clearing:rail-outbound), not the payee (ADR-15 (docs/DECISIONS.md)).
  The payee is metadata about the beneficiary (name, rail, masked ref,
  cooling-off status) used for authorization and display; the clearing account
  is what keeps double-entry balanced across the boundary. So: payee = who,
  clearing account = the accounting counter-leg.

  5) Is audit_log a per-transaction reducer result?

  No — and this is worth separating cleanly, because the word "reducer" is doing
  two different jobs:

  - The reducer is the posting operation on the ledger: balance_after = 
    balance_before + delta. That's how balance/held stay synced with the ledger
    (ADR-13 (docs/DECISIONS.md)). It has nothing to do with the audit log.
  - audit_log is not written per customer transaction. Ordinary transfers are
    already fully recorded by transaction + ledger_entry + outbox_event — that
    chain is the money audit trail.

  audit_log records privileged /admin-plane actions — the "who did what, when"
  for elevated operations: account freeze/unfreeze, limit changes, reversal
  approvals and executions, triggering a simulated inbound. It's
  append-only/immutable (ADR-8 (docs/DECISIONS.md)), one row per admin action.
  So it's admin-scoped governance, not a per-transaction fold.

● Great question — and you've put your finger on a real distinction that's worth
  being precise about. Let me answer it, then build the analytics manifest.

  Idempotency vs. duplicate suppression — two different problems

  - Idempotency (what the key gives us): the same request, retried, executes
    once. Its whole job is retry safety (network timeout, client resend).
  - Duplicate suppression (what you're describing): two distinct requests that 
    happen to be semantically identical — the double-click where the client
    mints a fresh key each click. The idempotency key, by design, does not catch
    this, because the two requests genuinely are different operations as far as
    the key is concerned.

  You're exactly right that a new key per click defeats it. Here's how I'd layer
  the defense:

  1. The primary fix is where the key is generated (client-side)

  The key should represent the user's intent, not the button press — so it's
  generated once when the transfer intent is created (form opened / "review"
  step reached) and reused across every click/retry of that same intent. Then a
  double-click sends the same key → deduped for free. "We generate a new one
  each click" is the client bug; generating once per intent is the standard
  (Stripe-style) pattern and solves the common case cleanly.

  But client-side controls are unreliable (two tabs, a buggy SPA, a scripted
  client), so we want a server backstop.

  2. The server backstop (the improvement you're asking about) — and it needs no
  new schema

  We already store request_fingerprint + owner_id + created_at on
  idempotency_key. So the balance service can run a soft duplicate-detection 
  window: on a new transfer, if an identical fingerprint (type, source, 
  destination, amount, currency) was seen for this owner within the last N
  seconds under a different key → treat it as a suspected duplicate. Crucially
  this is a soft control — warn and require an explicit confirmDuplicate (or a
  deliberate override), not a hard block, because legitimately paying the same
  person the same amount twice is a real thing. That's precisely the "you
  recently sent an identical payment — send again?" prompt banks use.

  3. What OTP + holds already buy you (and their limit)

  For external outbound, OTP + the hold do add genuine protection: each pending
  transfer needs its own out-of-band confirmation, and the hold reserves funds
  so you can't over-commit past available. So a double-submit is throttled by
  friction + fund reservation. But it's friction, not prevention (a user with
  balance could confirm both), and internal transfers have no OTP — so they're
  the real exposure and exactly where the soft window earns its keep.

  My recommendation

  Acceptable-as-is for the prototype baseline (key + OTP + holds + velocity
  limits is defensible). But the soft duplicate window is a cheap, high-value 
  hardening — no schema change, reuses request_fingerprint, and it's the only
  thing that covers internal transfers. I'd add it, documented as service
  behavior in spec 04 (not the schema). Want me to write that behavior into spec
  04 / a note in DATA-MODEL.md?

● Before I lock the window in, one clarification that actually matters for why
  we're adding it — because there's a subtle gap in the "OTP already prevents
  it" reasoning:

  How OTP is generated: the code is generated server-side by the balance service
  at initiation, bound to that specific transaction; the OTP app is the
  out-of-band channel that reveals it (it doesn't mint it). Single-use + TTL are
  correct.

  The subtlety: because the code is bound to a specific transaction, a
  double-submit that creates two distinct pending transactions (T1, T2) produces
  two distinct codes (C1, C2). Single-use stops replaying one code, but it does
  not stop the user fetching both codes from the OTP app and confirming both →
  two duplicate transfers succeed. So OTP single-use prevents code replay, not
  duplicate distinct transactions — which is exactly the gap the soft window
  fills. It's genuinely additive, not redundant.

  That said, you're right that it's not load-bearing: OTP friction (seeing two
  identical pendings, entering two codes) makes accidental duplication
  low-probability, so "additional layer" is the correct framing. 60s window,
